# chat-parser — мониторинг болей рынка оптики

Собирает историю открытых телеграм-чатов (владельцы оптик, персонал салонов,
оптометристы, покупатели), восстанавливает из плоского потока сообщений
диалоги, извлекает через Claude структурированные сигналы — боли, потребности,
задачи — и группирует их в ранжированный список проблем.

```
Telegram (MTProto)  ->  messages   ->  threads  ->  signals  ->  clusters  ->  отчёт
   ingest               Supabase       склейка       LLM         LLM        Markdown
                                       диалогов   + проверка  группировка
                                                    цитат     по аудитории
                                             |
                          Telegram-бот ------+  итоги дня в 22:00, топ болей, участники
```

Ключевой принцип: **модель не пишет отчёт по логам**. Она работает на одном
диалоге за раз и обязана подкреплять каждый сигнал дословной цитатой. Цитата
автоматически проверяется на вхождение в исходный текст; не прошла — сигнал
выбрасывается. Подсчёт, дедупликация и приоритизация — код, а не модель.

## Установка

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env
```

### Supabase

1. Создай проект на supabase.com.
2. Project Settings -> Database -> Connection string -> URI. Бери **Session
   pooler** (порт 5432) — он IPv4-совместимый; прямое подключение к БД у новых
   проектов работает только по IPv6. Transaction pooler (6543) тоже подойдёт:
   `db.py` поднимает asyncpg с `statement_cache_size=0`.
3. Положи строку в `DATABASE_URL` в `.env`, подставив пароль.
4. `chat-parser init-db` — накатит схему. Идемпотентно, можно гонять повторно.
   Альтернатива без CLI: SQL Editor -> New query -> содержимое `db/schema.sql`.

`init-db` включает на всех таблицах RLS без политик. Supabase публикует схему
`public` через REST API, и без RLS переписки мог бы прочитать любой, у кого
есть anon-ключ проекта. Пайплайн ходит напрямую под владельцем таблиц, и на
него RLS не действует.

Free tier (500 МБ) хватает с запасом: 300k сообщений ≈ 80 МБ. Сырой JSON
от Telegram намеренно не сохраняется.

### LLM

Годится любой OpenAI-совместимый шлюз — `LLM_BASE_URL`, `LLM_API_KEY`.
По умолчанию прописан `https://polza.ai/api/v1`.

`LLM_MODEL` **обязательно посмотреть у самого шлюза**, а не выписать из
головы: неверный id даёт 404 на каждом запросе.

```bash
chat-parser models              # весь каталог
chat-parser models --grep qwen  # только нужное
```

Шлюзы по-разному поддерживают структурированный вывод. `LLM_JSON_MODE=auto`
сам подберёт рабочий режим (`json_schema` -> `json_object` -> `text`) и
напечатает его в `doctor`; найденный режим можно зафиксировать в `.env`.

Если `doctor` пишет «нет JSON» или «израсходовала лимит на рассуждения» —
смотри сырой ответ:

```bash
chat-parser llm-test
```

«Думающие» модели (Qwen3 и подобные) сначала рассуждают и только потом
отвечают, и рассуждения съедают лимит токенов. `llm-test` покажет, сколько
ушло на них. Лечится выключением рассуждений через `LLM_EXTRA_BODY`
(имя параметра зависит от шлюза) или выбором версии модели без них.

### Telegram: аккаунт-сборщик (необязательно)

Нужен только для автоматической выгрузки. Без него работает всё остальное —
историю заливаешь вручную (см. ниже), и это правильный способ начать: он
ничем не рискует.

1. my.telegram.org -> API development tools -> `api_id` и `api_hash` в `.env`.
2. Разовый вход: `python scripts/login.py` -> полученную строку в
   `TG_SESSION_STRING`.

### Telegram: бот-панель

Отдельная сущность: токен у @BotFather в `TG_BOT_TOKEN`, свой id (@userinfobot)
в `TG_ADMIN_IDS`. Бот историю чатов читать не может — он только интерфейс;
собирает по-прежнему аккаунт через MTProto.

Если бот падает с «Cannot connect to host api.telegram.org» (в Windows —
«превышен таймаут семафора»), провайдер блокирует Telegram: приложение
обходит это само, программы — нет. Включи VPN на весь компьютер или пропиши
локальный прокси VPN-клиента в `TG_PROXY` (например,
`socks5://127.0.0.1:10808`). `doctor` проверяет связь с API ботов тем же
путём, что и бот.

`TG_ADMIN_IDS` обязателен: без него командовать ботом сможет любой, кто его
найдёт. `chat-parser bot` откажется стартовать с пустым списком.

Аккаунт нужен **отдельный, не основной**: массовая выгрузка — это против ToS
Telegram, и аккаунт могут заблокировать. Держи стабильный IP: user-аккаунт,
ходящий каждый день с нового адреса, выглядит подозрительно.

### Соль

```bash
python -c "import secrets; print(secrets.token_hex(16))"   # -> AUTHOR_SALT
```

Реальные `user_id` в базу не попадают — только солёный хэш. **Соль менять
нельзя**: это разорвёт связь сигналов с авторами в уже собранных данных.

## Ручная загрузка истории — без API-ключей

Самый безопасный способ начать: у аккаунта ничего не просят, вступать никуда
не надо, забанить не за что.

1. Telegram Desktop -> открыть чат -> **⋮** -> **Экспорт истории чата**
2. Формат **JSON**, медиа можно отключить — нужен только текст
3. В указанной папке появится `result.json`

```bash
chat-parser import-json "C:\\Users\\you\\Downloads\\ChatExport\\result.json"
chat-parser threads
chat-parser extract --limit 50
```

Либо просто **пришли `result.json` файлом боту** — он импортирует сам
(Telegram отдаёт ботам файлы до 20 МБ; экспорт крупнее заливай через консоль).

Импорт идемпотентный: гоняй повторно на обновлённом экспорте, дубликатов не
будет. Id чата приводится к тому же виду, в котором его видит Telethon, так
что позже можно добавить этот же чат через MTProto — данные сойдутся, а не
задвоятся, и досинхронизация продолжится с последнего импортированного
сообщения.

## Первый запуск

```bash
chat-parser doctor                                      # проверить всё разом
chat-parser add-chat "https://t.me/+HASH" --join        # приватный чат
chat-parser add-chat @optika_prof                       # публичный
chat-parser ingest --mode backfill --limit 2000         # пробная выгрузка
chat-parser threads                                     # склеить в диалоги
chat-parser extract --limit 50                          # 50 тредов на пробу
```

`doctor` проверяет конфиг, связь с Supabase, авторизацию в Telegram и доступ
к модели, и печатает понятный отчёт. Начинай всегда с него.

### Приватные чаты

Ссылка вида `t.me/+HASH` — приватное приглашение. Такой чат **нельзя читать,
не вступив в него**, поэтому нужен явный флаг `--join`: вступление это самое
рискованное для аккаунта действие, случайно оно происходить не должно.
Держись в пределах 5–10 вступлений в сутки.

Если группа с премодерацией, `add-chat` скажет «заявка отправлена» — повтори
команду после того, как админ одобрит.

Теперь **посмотри глазами** на таблицу `signals` в Supabase Table Editor.
Это главная проверка: сигналы осмысленные или модель льёт воду? Если плохо —
правится `src/chat_parser/analyze/prompts.py`, а не инфраструктура. Пока этот
шаг не выглядит убедительно, гнать полный backfill смысла нет.

Когда результат устраивает:

```bash
chat-parser ingest --mode backfill    # вся история, без limit
chat-parser threads
chat-parser extract
chat-parser cluster
chat-parser report
```

## Работа через Telegram-бота

После настройки `.env` консоль нужна только чтобы запустить бота. На Windows —
двойной щелчок по `scripts\start-bot.bat` (пока окно открыто, бот работает),
в остальных системах — `chat-parser bot`.

Кнопки внизу: **🔝 Топ болей за месяц · 💬 Список чатов · ➕ Добавить чат ·
👤 Инфо о человеке · ⏰ Время отчёта**. Остальное — команды в меню слева от
поля ввода (таблица ниже).

### Итоги дня

Каждый день в выбранное время (по умолчанию 22:00 по Москве) аккаунт-сборщик
забирает переписку подключённых чатов за сутки. Для контекста берутся и
предыдущие сутки: разговор, начатый вчера и продолженный сегодня, модель видит
целиком. Бот собирает обсуждения, разбирает законченные, раскладывает новые
сигналы по уже известным болям (номера болей не меняются), а то, что никуда
не подошло, собирает в новые боли. Затем приходит **одно** сообщение:

- **Чаты** — сколько сообщений, обсуждений и сигналов в каждом;
- **🧭 Главное за день** — 3–5 выводов;
- **О чём говорили** — какие боли всплывали;
- **🆕 Новые боли** — которых раньше не было, с цитатой;
- **🔥 Острые сигналы** — острота 4–5 из 5, с цитатой и ссылкой на сообщение;
- **📈 Всплески** — известная боль звучит заметно чаще обычного (`SPIKE_*`).

Остальное молча копится в базе и видно в топе и карточках болей. В остальное
время бот ничего не присылает. Если в назначенное время бот был выключен,
итоги придут сразу после запуска.

**⏰ Время отчёта** — готовые варианты кнопками или «✍️ Другое время» и
ответом любое время с минутами (`21:30`, `9`). Бот сразу пишет, когда придут
следующие итоги. Если новое время сегодня уже прошло, а сегодняшних итогов
ещё не было, бот предложит прислать их сейчас — иначе они придут завтра в
новое время. Два отчёта в один день не придут. `REPORT_HOUR` в `.env` — только
время по умолчанию, пока его не поменяли в боте.

Автоматический разбор тратит не больше `LIVE_DAILY_BUDGET` рублей в день
(считается по `LLM_PRICE_IN` / `LLM_PRICE_OUT`, ручные команды в лимит не
входят). Кончился лимит — в отчёте будет пометка, остальное разбирается
вручную через `/extract`. Архив, залитый файлом `result.json`, сам не
разбирается никогда — только вручную.

Скрытая команда **`/live`** (её нет в справке) показывает, сколько потрачено
сегодня, ставит вечерний разбор на паузу (переписка продолжает собираться,
нейросеть не запускается) и присылает итоги прямо сейчас, не отменяя вечерних.

### Участники и компании

**👤 Инфо о человеке** — ответить на подсказку одним сообщением: ник и через
запятую компания, роль, заметка.

```
@ivan_optika Оптика Люкс, владелец, знакомы по выставке
@maria_opt Линзы Плюс
@olga_lens роль: оптометрист
```

Можно по строкам (первая — ник), можно подписать поле («роль:», «заметка:»),
вместо ника — `/who_1a2b3c4d`. Не присланное не меняется. Сообщение вида
«@ник текст» работает и без кнопки, а один `@ник` без текста — это по-прежнему
добавление чата. Человека ищут сначала среди тех, кто писал в чатах, потом в
самом Telegram — так можно записать того, кто ещё ничего не писал: когда он
напишет, подпись под его цитатами уже будет готова.

Под каждой цитатой — кто её сказал: имя из Telegram и ссылка `/who_1a2b3c4d`.
Она открывает карточку человека: в каких чатах пишет, сколько сигналов, какие
боли поднимал. Кнопка **✏️ Компания и роль** — ответить одной строкой
«Оптика Люкс, владелец», **📝 Заметка** — любой текст («-» стирает). После
этого подпись под цитатами везде становится «Иван Петров · Оптика Люкс,
владелец».

Если человек сам написал о себе («у меня два салона Оптика Люкс»), нейросеть
предложит компанию и роль — в карточке появится 💡 с цитатой и кнопка
«✅ Верно, сохранить подсказку». Сама она ничего не записывает, а слова о
других людях («у Ивана своя оптика») не считаются.

Список участников чата — кнопка 👥 рядом с чатом в **💬 Список чатов** (или
`/people` — все чаты сразу). Имена копятся по мере загрузки переписки; для
старых данных — кнопка «🔄 Подтянуть имена из Telegram» в списке участников
или повторная отправка `result.json`.

В **💬 Список чатов** рядом с каждым чатом — **🗑 Удалить** (с подтверждением):
бот перестаёт следить за чатом и удаляет его переписку и сигналы, боли
пересчитываются без него. Из самого чата в Telegram аккаунт не выходит.

### Добавление чатов и ручная работа

**➕ Добавить чат** — прислать ссылку (`t.me/имя`, `@имя` или приглашение
`t.me/+…`). С ключами Telegram API бот подключает чат (в закрытый — только
после подтверждения кнопкой), загружает историю с прогрессом и кнопкой ⏹ и
предлагает разобрать. Без ключей — запоминает ссылку в `chat_requests` и
подключает сохранённые чаты, как только ключи появятся: при запуске бота, по
кнопке «🔌 Подключить сейчас» в `/chats` и при `/run` (не больше
`JOIN_PER_RUN` вступлений за раз). Остановленная загрузка истории
продолжается с того же места.

Архив из файла разбирается вручную:

1. Пришли боту файлом `result.json` (экспорт чата из Telegram Desktop). Бот
   загрузит историю, разделит её на обсуждения и спросит, сколько разобрать.
2. Выбери **20** — это проба. Бот покажет прогресс и итог, а в следующий раз
   — сколько времени займёт вся очередь.
3. `/cluster` — группировка сигналов в боли и описание каждой боли.
4. `/top` — рядом с каждой болью нажимаемая ссылка `/pain_12` с
   подробностями и цитатами. `/report` — всё одним файлом.

«Обсуждение» в боте — то же, что тред в коде: вопрос и ответы на него,
восстановленные из общего потока сообщений. Один тред — один запрос к модели.

Под любой долгой операцией (разбор, пересчёт болей, полный цикл) есть кнопка
**⏹ Остановить**: новых запросов к модели не будет, уже сделанное
сохраняется. Любое меню закрывается кнопкой «Отмена». Фоновую операцию можно
остановить кнопкой из `/status`.

По расписанию работает только вечерний разбор — в пределах дневного лимита.
Всё остальное запускается вручную, и дорогие операции никогда не берут всю
очередь молча: разбор всегда спрашивает объём, `/run` при очереди больше
`BOT_CONFIRM_THRESHOLD` обсуждений просит подтверждение. Одновременно идёт
одна тяжёлая операция; вечерний отчёт, если что-то уже идёт, подождёт.

Расход токенов пользователю бота не показывается. Он пишется в таблицу
`llm_usage` на каждом этапе (включая остановленные операции) и виден только по
скрытой команде **`/usage`** — её нет ни в меню, ни в справке: за сутки,
неделю, месяц, в среднем на обсуждение, на разбор и на пересчёт болей. Если
задать `LLM_PRICE_IN` / `LLM_PRICE_OUT` (цена за 1 млн токенов), там же будет
стоимость. При запуске бот сам обновляет схему базы, так что новые таблицы
появляются без ручного `init-db`.

| Команда | Что делает |
|---|---|
| 🔝 Топ болей за месяц | главные боли по сигналам за 30 дней, по аудиториям |
| 💬 Список чатов, `/chats` | чаты со ссылками, участники, удаление, чаты в ожидании |
| ➕ Добавить чат | прислать ссылку — чат подключится |
| 👤 Инфо о человеке | «@ник компания, роль, заметка» — записать, кто это |
| ⏰ Время отчёта, `/time` | во сколько присылать итоги дня |
| `/who_<код> [компания, роль, заметка]` | карточка участника; с текстом — записать сведения |
| `/people` | все участники с компаниями и ролями |
| `/status` | что собрано, очередь, сколько сигналов и болей, что выполняется |
| `/extract [N]` | разобрать N обсуждений; без числа — меню с оценкой времени |
| `/cluster` | сгруппировать сигналы в боли, написать карточки, обновить отчёт |
| `/top [N]` | топ болей за всё время |
| `/pain_<номер>` | карточка боли с цитатами и гипотезами (ссылки есть в топе) |
| `/signals [N]` | последние сигналы — для калибровки промпта |
| `/report` | отчёт файлом |
| `/redo` | вернуть разобранное в очередь после правки промпта |
| `/retry` | повторить обсуждения, которые не удалось разобрать |
| `/run` | полный цикл одной кнопкой |
| файл `result.json` | импорт истории чата |
| `/addchat <ссылка>` | то же, что кнопка ➕ Добавить чат |
| `/help` | справка |

Бот отвечает, пока запущен: выключенный компьютер или сон — бот молчит.
Чтобы он был доступен всегда, его запускают на сервере.

Systemd-юнит:

```ini
[Service]
WorkingDirectory=/opt/chat-parser
ExecStart=/opt/chat-parser/.venv/bin/chat-parser bot
Restart=always
```

Без бота полный цикл запускается из консоли: `chat-parser pipeline`.

Всё в пайплайне идемпотентно: упало посреди прогона — перезапусти, дубликатов
не будет. `chat-parser status` показывает курсоры, размер выгрузки и очередь
тредов на анализ.

## Команды

| Команда | Что делает |
|---|---|
| `init-db` | Накатывает схему в Supabase |
| `doctor` | Проверяет конфиг, БД, Telegram и доступ к модели |
| `import-json <файл>` | Заливает историю из экспорта Telegram Desktop |
| `add-chat @a @b [--join]` | Резолвит чаты и заводит их в БД |
| `ingest --mode backfill\|incremental` | Выгрузка истории / досинхронизация |
| `threads` | Склейка сообщений в диалоги |
| `extract` | Извлечение сигналов через Claude |
| `cluster` | Группировка в боли, скоринг, карточки |
| `report` | `out/report.md` |
| `status` | Состояние по каждому чату |
| `models` | Каталог моделей на шлюзе |
| `llm-test` | Сырой ответ модели — когда doctor говорит «нет JSON» |
| `bot` | Телеграм-бот: команды и итоги дня |
| `pipeline` | Всё вышеперечисленное инкрементально |

## Как это устроено

**Треды.** В групповом чате реплика разорвана на пять сообщений и перемешана
с двумя параллельными разговорами. `normalize/threads.py` восстанавливает
диалоги: жёсткие рёбра по `reply_to`, мягкая эвристика по временному окну и
участникам для остального.

**Аудитории.** У владельца оптики и у покупателя очков боли не пересекаются
(закупка линз, персонал, аренда vs. подбор оправы, цена прогрессивов).
Поэтому у каждого сигнала есть поле `audience`, и кластеризация идёт **внутри**
аудитории — иначе отчёт превращается в кашу.

**Кластеризация.** Группируем моделью, а не эмбеддингами: формулировки
сигналов короткие, и на таком масштабе модель справляется лучше подбора
порогов косинуса. Но контекст обычной модели через шлюз — десятки тысяч
токенов, а не миллион, поэтому проход двухступенчатый: сигналы режутся на
батчи по `CLUSTER_BATCH` и кластеризуются независимо, а второй проход
схлопывает дубликаты между батчами. Порог перехода на pgvector + HDBSCAN —
примерно 5000 сигналов.

**Скоринг.** Считается по **уникальным авторам и чатам**, а не по числу
сигналов. Без этого топ занимают один болтливый участник и один самый
активный чат.

## Качество

Автоматическая часть уже встроена: доля отбракованных цитат печатается после
каждого `extract`. Устойчиво выше 5% — проблема в промпте.

Ручная часть, которую стоит завести до того, как доверять отчёту: размети
руками 30 тредов в Supabase (что здесь боль, а что нет) и считай на них
precision/recall после каждой правки промпта. Ориентир для рабочего состояния —
precision ≥ 0.8.

## Стоимость

Зависит от тарифа шлюза. Порядок величин при 5–10 чатах: разовый backfill —
единицы тысяч запросов на извлечение, инкремент — десятки-сотни запросов в
сутки. Основной объём даёт стадия `extract` (один запрос на тред), поэтому
если захочешь удешевить — ставь на неё модель попроще через `LLM_MODEL`, а
на `LLM_MODEL_SYNTH` оставляй модель посильнее: кластеризация и карточки
запускаются в тысячи раз реже, а качество отчёта определяют они.

Решать это стоит по замерам на размеченном наборе, а не на глаз.

## Правовая рамка

Сообщения в открытых чатах — всё равно персональные данные. Здесь сделано:
контакты маскируются на записи, реальные `user_id` не хранятся (только хэш с
солью), в модель уходят псевдонимы вида `u:1a2b3c4d` — ни имён, ни `@ников`.
Имена и ники из Telegram, а также компании и роли, которые ты вносишь, лежат в
таблице `authors` только для подписей в боте; на всех таблицах включён RLS.
Чего делать не стоит: публиковать цитаты вместе с именами авторов и
использовать результат для рассылок по этим же людям.

## Тесты

```bash
pytest -q
```

Сквозной тест бота (настоящие обработчики, фейковый Telegram, подставная
модель) нужна тестовая база — таблицы в ней пересоздаются:

```bash
TEST_DATABASE_URL=postgresql://user@localhost:5432/chatparser_test pytest -q
```

Покрыта чистая логика: маскирование ПД, склейка тредов, отбраковка
галлюцинаций, согласование режима JSON со шлюзом, расписание планировщика.
